## 핵심 개념 되새김

- **HTML·CSS·JS 역할 분담**: HTML은 페이지의 **구조**(어떤 요소가 있는지)를 짜고, CSS는 그 구조에 **표현**(색·배치·크기 같은 스타일)을 입히고, JS는 클릭 같은 이벤트에 반응해 **동작**(클래스를 토글하는 등)을 만든다. 다크모드 버튼을 예로 들면 JS는 `body`에 `dark` 클래스를 붙였다 뗐다만 할 뿐, 실제로 배경색이 바뀌는 건 CSS가 그 클래스에 스타일을 정의해뒀기 때문이다.
- **commit과 push의 차이**: commit은 지금까지의 변경 내용을 로컬 저장소(`.git`)에 하나의 스냅샷으로 기록하는 것이고, push는 그렇게 쌓인 로컬 커밋들을 GitHub 같은 원격 저장소로 실제로 전송하는 것이다. commit만 하고 push를 안 하면 내 컴퓨터에만 기록이 남고 GitHub에는 아무 변화가 없다.
- **F12 Network 요청과 응답(200)**: 브라우저가 페이지를 열 때 `index.html`·`style.css`·`script.js` 같은 파일을 서버(Live Server)에 각각 요청(`GET`)하고, 서버가 파일을 잘 찾아 돌려주면 응답 상태 코드로 `200`을 준다. `200`은 "요청한 자원을 정상적으로 찾아서 보냈다"는 뜻이다.

## 자유 로그

오늘 커밋 메시지를 잘못 입력하는 시행착오를 겪었다. 처음 커밋할 때 메시지를 `"자기소개 페이지 초기 버전"`이라고 쓰려다가 인코딩 문제인지 `"자기소 페이지 초기 버"`처럼 잘려서(혹은 깨져서) 들어갔다. 이미 push까지 끝난 상태라 그냥 두면 원격 히스토리에 이상한 메시지가 영구히 남는 상황이었다.

처음엔 새 커밋을 하나 더 추가해서 올바른 메시지("자기소개 페이지 초기 버전")로 덮어씌우듯 넘어갔는데, 그러면 히스토리에 잘못된 커밋이 그대로 남아있는 게 마음에 걸려서 완전히 지우고 싶었다. Claude Code한테 물어봤더니 `git commit-tree`로 기존 커밋의 최종 파일 상태(tree)만 가져와서 부모 없는 새 커밋 하나를 처음부터 다시 만들고, `git reset --hard`로 브랜치를 그 커밋으로 옮긴 다음, `git push --force-with-lease`로 원격까지 덮어쓰는 방법을 알려줬다. 그렇게 해서 최종적으로는 올바른 메시지의 커밋 하나만 남기는 데 성공했다.

배운 점: 커밋 메시지는 push 전이면 `git commit --amend`로 간단히 고칠 수 있지만, 이미 push된 뒤라면 강제 push(`--force-with-lease`)가 필요하고 이건 원격 히스토리를 덮어쓰는 위험한 작업이라 신중해야 한다는 걸 알았다. 협업 중인 저장소였다면 다른 사람 작업을 날릴 수도 있어서, 이번처럼 혼자 쓰는 저장소가 아니었다면 더 조심했어야 할 것 같다.

AI에게 물어본 것: 오늘은 AI를 쓰는 실습 단계는 없었지만, 위 커밋 메시지 문제를 Claude Code에게 물어봤다. `git commit-tree`로 새 루트 커밋을 만드는 방법을 제안받았고, 실행 전에 각 명령어가 무엇을 하는지 설명을 들은 뒤 `git log --oneline --all`로 커밋이 하나로 정리됐는지, `git status`로 origin과 동기화됐는지 직접 확인하고 진행했다.

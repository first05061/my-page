# my-page — 개인 소개 페이지 + 프론트엔드·백엔드 연동

클라우드컴퓨팅실습 **개인 과제** 결과물입니다.
1주차에 만든 개인 소개 페이지에, FastAPI로 만든 백엔드 API와 연동되는
**방명록 페이지**를 붙였습니다.

---

## 프로젝트 소개

정적 HTML로 만든 개인 소개 페이지(Vercel)에서 링크를 타고 들어가면,
Render에 배포한 FastAPI 백엔드를 `fetch`로 호출해 그 결과를 보여주는
방명록 페이지가 열립니다.

브라우저에서 "등록" 버튼을 한 번 누르면
**Vercel(화면) → Render(API) → 데이터베이스(저장)** 로 요청이 이동하고,
목록을 다시 받아와 화면이 갱신됩니다.

| 계층 | 기술 | 역할 | 배포처 |
|---|---|---|---|
| 개인 소개 페이지 | HTML · CSS · JavaScript | 자기소개 | Vercel |
| 프론트엔드 | HTML · CSS · JavaScript (`fetch`) | 백엔드 API 호출 및 결과 표시 | Vercel |
| 백엔드 | FastAPI · SQLAlchemy | 소개 정보 제공, 방명록 CRUD | Render |
| 데이터베이스 | SQLite | 방명록 저장 | (백엔드 서버 내부) |

### API 엔드포인트

| 메서드 | 경로 | 설명 |
|---|---|---|
| `GET` | `/` | 서비스 안내 |
| `GET` | `/health` | 서버 생존 확인 |
| `GET` | `/profile` | 개인 소개 정보(JSON) |
| `GET` | `/entries` | 방명록 목록 조회 |

전체 명세와 테스트 화면은 배포된 백엔드의 `/docs`(Swagger UI)에서 확인할 수 있습니다.

## 로컬에서 실행하기

**백엔드** (터미널 1)

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

→ http://127.0.0.1:8000/docs 에서 Swagger UI 확인

**프론트엔드** (터미널 2)

```bash
python -m http.server 8080
```

→ http://127.0.0.1:8080/index.html 접속 후 방명록 링크로 이동.
로컬 백엔드를 보게 하려면 주소 뒤에 `?api=http://127.0.0.1:8000` 을 붙입니다.

배포 절차는 [DEPLOY.md](DEPLOY.md)에 정리해 두었습니다.

## 1주차 실습 기록

### 핵심 개념 되새김

- **HTML·CSS·JS 역할 분담**: HTML은 페이지의 **구조**(어떤 요소가 있는지)를 짜고, CSS는 그 구조에 **표현**(색·배치·크기 같은 스타일)을 입히고, JS는 클릭 같은 이벤트에 반응해 **동작**(클래스를 토글하는 등)을 만든다. 다크모드 버튼을 예로 들면 JS는 `body`에 `dark` 클래스를 붙였다 뗐다만 할 뿐, 실제로 배경색이 바뀌는 건 CSS가 그 클래스에 스타일을 정의해뒀기 때문이다.
- **commit과 push의 차이**: commit은 지금까지의 변경 내용을 로컬 저장소(`.git`)에 하나의 스냅샷으로 기록하는 것이고, push는 그렇게 쌓인 로컬 커밋들을 GitHub 같은 원격 저장소로 실제로 전송하는 것이다. commit만 하고 push를 안 하면 내 컴퓨터에만 기록이 남고 GitHub에는 아무 변화가 없다.
- **F12 Network 요청과 응답(200)**: 브라우저가 페이지를 열 때 `index.html`·`style.css`·`script.js` 같은 파일을 서버(Live Server)에 각각 요청(`GET`)하고, 서버가 파일을 잘 찾아 돌려주면 응답 상태 코드로 `200`을 준다. `200`은 "요청한 자원을 정상적으로 찾아서 보냈다"는 뜻이다.

### 자유 로그

오늘 커밋 메시지를 잘못 입력하는 시행착오를 겪었다. 처음 커밋할 때 메시지를 `"자기소개 페이지 초기 버전"`이라고 쓰려다가 인코딩 문제인지 `"자기소 페이지 초기 버"`처럼 잘려서(혹은 깨져서) 들어갔다. 이미 push까지 끝난 상태라 그냥 두면 원격 히스토리에 이상한 메시지가 영구히 남는 상황이었다.

처음엔 새 커밋을 하나 더 추가해서 올바른 메시지("자기소개 페이지 초기 버전")로 덮어씌우듯 넘어갔는데, 그러면 히스토리에 잘못된 커밋이 그대로 남아있는 게 마음에 걸려서 완전히 지우고 싶었다. Claude Code한테 물어봤더니 `git commit-tree`로 기존 커밋의 최종 파일 상태(tree)만 가져와서 부모 없는 새 커밋 하나를 처음부터 다시 만들고, `git reset --hard`로 브랜치를 그 커밋으로 옮긴 다음, `git push --force-with-lease`로 원격까지 덮어쓰는 방법을 알려줬다. 그렇게 해서 최종적으로는 올바른 메시지의 커밋 하나만 남기는 데 성공했다.

배운 점: 커밋 메시지는 push 전이면 `git commit --amend`로 간단히 고칠 수 있지만, 이미 push된 뒤라면 강제 push(`--force-with-lease`)가 필요하고 이건 원격 히스토리를 덮어쓰는 위험한 작업이라 신중해야 한다는 걸 알았다. 협업 중인 저장소였다면 다른 사람 작업을 날릴 수도 있어서, 이번처럼 혼자 쓰는 저장소가 아니었다면 더 조심했어야 할 것 같다.

AI에게 물어본 것: 오늘은 AI를 쓰는 실습 단계는 없었지만, 위 커밋 메시지 문제를 Claude Code에게 물어봤다. `git commit-tree`로 새 루트 커밋을 만드는 방법을 제안받았고, 실행 전에 각 명령어가 무엇을 하는지 설명을 들은 뒤 `git log --oneline --all`로 커밋이 하나로 정리됐는지, `git status`로 origin과 동기화됐는지 직접 확인하고 진행했다.

### 핵심 개념 되새김

- **3계층이 맡는 일**: 프론트엔드(Vercel)는 화면을 그리고 사용자의 입력을 받는다. 백엔드(Render, FastAPI)는 그 요청을 받아 규칙에 맞는지 검사하고 처리해 JSON으로 돌려준다. 데이터베이스는 그 결과를 서버가 꺼졌다 켜져도 남도록 저장한다. 화면은 데이터를 "보여줄" 뿐 "갖고 있지" 않다는 점이 핵심이다.
- **`fetch`가 하는 일**: 브라우저가 다른 주소의 서버에 HTTP 요청을 보내고 응답을 받아오는 함수다. 응답이 올 때까지 시간이 걸리므로 `async/await`로 기다렸다가, `JSON.stringify`로 보낼 객체를 JSON 문자열로 바꾸고 `res.json()`으로 받은 JSON을 다시 객체로 되돌린다. 보낼 때와 받을 때 한 번씩 변환이 필요하다.
- **CORS가 필요한 이유**: 브라우저는 페이지가 열린 출처(도메인·포트)와 다른 곳으로 보낸 요청의 응답을 기본적으로 차단한다. Vercel 주소의 페이지가 Render 주소의 API를 부르려면 백엔드가 "이 출처는 허용한다"고 선언해야 한다. 이때 막는 쪽은 서버가 아니라 브라우저이고, 서버는 멀쩡히 응답하고 있다는 점이 헷갈리기 쉽다.
- **바뀌는 값은 코드가 아니라 환경변수로**: 허용 출처(`ALLOWED_ORIGINS`)나 DB 접속 문자열(`DATABASE_URL`)은 로컬과 배포 환경에서 값이 다르다. 코드에 박아 두면 환경이 바뀔 때마다 코드를 고쳐야 하므로, 환경변수로 빼고 코드에는 기본값만 둔다.

### 자유 로그

1주차에 만든 `my-page` 저장소를 그대로 이어받아, 여기에 `backend/` 폴더를 추가하는 방식으로 구성했다.
워크북처럼 저장소를 둘로 나눌 수도 있었지만, 제출할 GitHub 주소가 하나로 정리되는 편이 낫다고 판단했다.
Render는 Root Directory 설정으로 저장소 안의 하위 폴더만 골라 배포할 수 있어서 한 저장소로도 문제가 없었다.

워크북은 프론트엔드를 React(Vite)로 만들지만, 1주차 소개 페이지가 순수 HTML이라 여기에 React를 끼워 넣으면 구조가 어색해진다.
그래서 `fetch`만 쓰는 순수 JavaScript로 만들었다. 호출하는 부분(`fetch` → `await res.json()` → 화면 갱신)은 React 버전과 하는 일이 같다.

막힌 곳과 푼 과정:

- **시간이 9시간 어긋나는 문제.** 서버에 `datetime.now()`로 저장하면 Render 서버(UTC)와 내 화면(한국 시간)이 9시간 차이가 난다. 서버는 항상 UTC로 저장하고(`datetime.now(timezone.utc)`), 프론트에서 표준시 표시가 없는 문자열이면 `Z`를 붙여 `toLocaleString("ko-KR")`로 바꿔 보여주도록 했다.
- **CORS 기본값이 안 먹던 문제.** `os.getenv("ALLOWED_ORIGINS", 기본값)`은 변수가 **빈 문자열**로 존재하면 기본값을 쓰지 않고 빈 값을 그대로 가져온다. 실제로 로컬 테스트에서 허용된 출처인데도 preflight가 `400`으로 거부되어 찾아냈다. `os.getenv("ALLOWED_ORIGINS") or 기본값`으로 고쳤다.
- **로컬 테스트용 포트 5500이 막혀 있던 문제.** Windows에서 예약된 포트 범위에 걸려 `WinError 10013`이 났다. 8080으로 바꿔 해결했고, 백엔드 기본 허용 출처에 8080과 5500을 모두 넣어 두었다.

AI에게 시킨 것과 검증 방법: Claude Code에게 과제 안내와 실습 워크북을 주고, 1주차 `my-page`에 이어 붙이는 형태로 백엔드와 연동 페이지를 만들게 했다.
결과는 코드를 읽는 것만으로 믿지 않고, 로컬에서 백엔드를 실제로 띄워 `curl`로 하나씩 확인했다 —
`POST /entries`가 `201`과 `id`를 돌려주는지, `GET /entries`에 그 글이 보이는지, 없는 `id`를 `DELETE`하면 `404`인지,
빈 값을 보내면 `422`인지, 허용한 출처의 preflight는 `200`이고 허용하지 않은 출처는 `400`인지까지 직접 요청을 보내 확인했다.
위에 적은 CORS 기본값 버그는 이 과정에서 나온 것이다.
